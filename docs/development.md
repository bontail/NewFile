# Сборка и выпуск версий

## Требования

- macOS 13+ на Apple Silicon.
- Xcode Command Line Tools или полный Xcode: Swift, SDK macOS, Python 3,
  `codesign` и `ditto`.
- Для публикации — репозиторий GitHub с включённым GitHub Actions.

Swift Package Manager, сторонние библиотеки и отдельный проект Xcode не нужны.

## Команды

```sh
bash test.sh
bash build.sh
bash package.sh
```

`test.sh` проверяет файловые операции, конкурентное создание, защиту от перезаписи,
сохранение настроек, шаблоны и полноту переводов на 10 языков.

`build.sh` компилирует приложение и Finder Sync extension для `arm64`, копирует
локализации, подписывает оба компонента и проверяет подпись. По умолчанию результат
попадает в `dist/NewFile.app` и регистрируется в Launch Services и PlugInKit.

`package.sh` запускает тесты и собирает чистую копию в `.build/package.*` без
регистрации в системе. Затем создаёт архив и SHA-256 в `release/`.
Внутри архива: `NewFile/NewFile.app`, README, документация и `Source/`
с исходниками и скриптами сборки. Компиляторные кэши не включаются.
Уже установленное приложение и `dist/NewFile.app` упаковка не заменяет.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `NEWFILE_OUTPUT_DIR` | `dist` | Каталог приложения при вызове `build.sh` |
| `NEWFILE_REGISTER_APP` | `1` | `0` отключает регистрацию локальной сборки |
| `NEWFILE_PACKAGE_DIR` | `release` | Каталог архива и контрольной суммы |
| `NEWFILE_BUILD_NUMBER` | `4` | Положительный целочисленный `CFBundleVersion` |
| `NEWFILE_SIGNING_IDENTITY` | `-` | Имя установленного сертификата; `-` означает ad-hoc |

В CI регистрация всегда отключена. Версия приложения и расширения, а также имя
архива берутся из `VERSION` в формате `X.Y.Z`. GitHub Actions задаёт номер сборки
через `github.run_number`.

Пример отдельной локальной сборки:

```sh
NEWFILE_OUTPUT_DIR="$PWD/.build/check-dist" NEWFILE_REGISTER_APP=0 bash build.sh
```

Кэш модулей разделяется по пути проекта и версии компилятора. Если Command Line
Tools содержит повторное объявление SwiftBridging, `toolchain.sh` применяет
локальный VFS overlay, не изменяя системные файлы.

## Первый push

Создайте на GitHub пустой репозиторий без автоматически добавленного README.
Выполните из папки проекта, заменив URL адресом своего репозитория:

```sh
git init -b main
git add .
git commit -m "Initial release of NewFile"
git remote add origin https://github.com/bontail/NewFile.git
git push -u origin main
```

Каталоги сборки и ZIP-архивы исключены через `.gitignore`.
После push на вкладке Actions запустится проверка.

## GitHub Actions

Workflow: [Build and Release](../.github/workflows/release.yml).

| Событие | Результат |
| --- | --- |
| Push в `main` | Тесты, сборка, проверка подписи, архив в артефактах Actions |
| Pull request | Те же проверки без публикации релиза |
| Ручной запуск | Те же проверки для выбранной ветки или тега |
| Push тега `vX.Y.Z` | Проверки и GitHub Release с ZIP и SHA-256 |

Сборка выполняется на `macos-15` (Apple Silicon). Артефакты Actions сохраняются
14 дней. Публикация использует именно архив успешно завершившейся сборки,
проверяет его SHA-256 и получает право `contents: write` только в отдельной
задаче выпуска. Pull request выполняется с доступом только на чтение.
Версии официальных Actions зафиксированы по commit SHA.

## Выпуск

1. Обновите `VERSION`, например на `3.1.1`.
2. Проверьте сборку локально и выполните [ручную проверку Finder](troubleshooting.md#проверка-перед-выпуском).
3. Закоммитьте и отправьте изменения в `main`.
4. Создайте и отправьте соответствующий тег:

   ```sh
   git tag v3.1.1
   git push origin v3.1.1
   ```

5. Дождитесь успешного workflow и проверьте файлы в GitHub Releases.

Тег должен точно совпадать с `v` + содержимое `VERSION`; иначе сборка завершается
до компиляции. Поддерживаются стабильные версии `vX.Y.Z`.
Повторный запуск workflow не перезаписывает уже существующий релиз.
Для исправленного выпуска увеличьте версию и создайте новый тег.

Проверка скачанного архива в macOS:

```sh
shasum -a 256 -c NewFile-3.1.1-macOS-arm64.zip.sha256
```

## Подпись и нотарификация

По умолчанию локальные и CI-сборки используют ad-hoc подпись. Она проверяет
целостность пакета, но не подтверждает разработчика для Gatekeeper.
Workflow не импортирует сертификаты и не отправляет приложение на нотарификацию.

Для локальной подписи уже установленным сертификатом:

```sh
NEWFILE_SIGNING_IDENTITY="имя сертификата" bash package.sh
```

Для распространения с Developer ID нужны отдельные настройки hardened runtime,
сертификат и нотарификация Apple; один выбор сертификата не выполняет эти шаги.
Не добавляйте сертификаты, пароли и приватные ключи в репозиторий.
